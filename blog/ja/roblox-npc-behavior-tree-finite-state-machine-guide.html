商用ゲーム開発では、全体状態を制御する有限ステートマシン（FSM）と、細かな戦術を切り替えるビヘイビアツリー（BT）を組み合わせます。本稿ではブラックボード設計、視界コーンのレイキャスト、AI LODによる負荷分散を徹底解説します。

1. 有限ステートマシン（FSM）とビヘイビアツリー（BT）の使い分け

敵の複雑さに応じた適切な設計パターンの選択：

  • 有限ステートマシン（FSM）： 巡回、警戒、追跡、攻撃など、明確な段階を持つ敵に最適。Enter、Update、Exitの各フェーズが分離されます。
  • ビヘイビアツリー（BT）： 遮蔽物の利用、回復、武器切り替えなど、状況に応じた柔軟な優先順位判断を行うボスAIに不可欠。
  • ハイブリッド構成： 大枠の行動状態はFSMで管理し、戦闘状態内部の微細な戦術判断をビヘイビアツリーに委ねる手法が業界標準です。

2. 共有ブラックボード（Blackboard）と視界コーン知覚

サーバー負荷を抑えつつ自然な索敵を実現する仕組み：

  • ブラックボード： 標的プレイヤー、最後の目撃座標、警戒度などを一括管理し各ノードで共有するデータ領域。
  • 視界コーンとレイキャスト： 内積（Dot Product）で前方110度の視野内かを判定し、遮蔽物がないかをレイキャストで確認。
  • レイキャスト頻度の制御： 毎フレーム回すのではなく、0.2〜0.4秒間隔でNPC群を交互にスタッガー実行します。

3. Production Implementation Architecture

ServerScriptService.NPCFramework.StateMachine
-- Modular Finite State Machine for Roblox NPC
local StateMachine = {}
StateMachine.__index = StateMachine

function StateMachine.new(npcInstance, states, initialState)
    local self = setmetatable({}, StateMachine)
    self.NPC = npcInstance
    self.States = states
    self.CurrentState = nil
    self.Blackboard = {
        Target = nil,
        LastSeenPos = nil,
        Health = 100,
        PatrolPoints = {}
    }

    self:ChangeState(initialState)
    return self
end

function StateMachine:ChangeState(newStateName)
    if self.CurrentState and self.States[self.CurrentState].Exit then
        self.States[self.CurrentState]:Exit(self.NPC, self.Blackboard)
    end

    self.CurrentState = newStateName
    if self.States[newStateName] and self.States[newStateName].Enter then
        self.States[newStateName]:Enter(self.NPC, self.Blackboard)
    end
end

function StateMachine:Update(dt)
    if self.CurrentState and self.States[self.CurrentState].Update then
        local nextState = self.States[self.CurrentState]:Update(self.NPC, self.Blackboard, dt)
        if nextState and nextState ~= self.CurrentState then
            self:ChangeState(nextState)
        end
    end
end

return StateMachine

4. ビヘイビアツリーノード：セレクターとシーケンス

優先順位の階層的組み立て：

  • セレクターノード（?）： 左から順に評価し、1つでも成功すれば完了（攻撃 -> 射程外なら追跡 -> 見失えば巡回）。
  • シーケンスノード（&）： 全ての処理が成功して初めて完了（接近 -> 攻撃モーション -> ダメージ判定）。
  • デコレーターノード： クールダウンや成否反転などの条件修飾。

5. サーバー最適化：AI LODとオブジェクトプール

100体以上の敵がいてもサーバー60 FPSを維持するテクニック：

  • AI LOD： プレイヤー近傍は10Hzで高精度更新、遠方は1Hzに落とし、500 Stud以遠は物理演算を完全停止。
  • クライアント補間： サーバーは中継点（ウェイポイント）のみを指定し、歩行アニメーションと旋回はクライアントに委ねます。
  • オブジェクトプーリング： 毎回スポーン・破棄を繰り返さず、事前生成したモデルのCFrameと透明度を切り替えて再利用します。

Frequently Asked Questions

NPCが30体を超えるとサーバーが重くなる原因は？

全NPCが毎フレーム全速力でレイキャストやパス計算を行っているためです。AI LODで遠方の計算頻度を下げてください。

ビヘイビアツリーがステートマシンより優れている点は？

新アクションを追加する際に既存の遷移網を書き換える必要がなく、ツリーにノードを挿入するだけで済む拡張性の高さです。

敵が壁を透過して見つけてしまうのを防ぐには？

NPCの頭部からプレイヤーへレイキャストを飛ばし、障害物がヒットしないか確認する遮蔽判定を実装します。

クライアント側でAIの思考を処理しても大丈夫？

チートや同期崩れを防ぐため、標的決定やダメージ計算は必ずサーバーで実行し、クライアントは見た目の補間のみを担当させます。
