로블록스 퀘스트 아키텍처: DAG 의존성 그래프, 유한 상태 머신 & 분기형 대화 트리

By DopaBrain 로블록스 시스템 엔지니어링 팀 • 2026-09-29 • Technical Guide
시스템 아키텍처 공리: 수십 개의 불리언(Boolean) 변수로 퀘스트를 주먹구구식 추적하면 로직이 스파게티처럼 꼬이고 세이브 데이터가 오염됩니다. 대규모 RPG는 퀘스트를 방향성 비순환 그래프(DAG)로 모델링하고 이벤트 버스 기반의 유한 상태 머신(FSM)으로 제어해야 합니다.

퀘스트와 대화 시스템은 로블록스 RPG, 어드벤처, 스토리 게임의 서사를 이끄는 핵심 척추입니다. 아키텍처가 부실하면 퀘스트 포기, 컷신 중 튕김 현상에서 데이터가 영구 증발합니다.

선행 조건을 관리하는 DAG(Directed Acyclic Graph), 결합도를 낮춘 이벤트 버스 리스너, 플레이어의 선택에 따라 분기하는 대화 트리, 그리고 DataStore 용량을 90% 아끼는 비트필드 압축 저장 기법을 심층 분석합니다.

1. 방향성 비순환 그래프(DAG)로 설계하는 퀘스트 라인

순환 의존성 데드락 없는 안정적인 스토리 트리 구축:

  • 선행 조건 트리(Prerequisite Tree): 메인 스토리와 서브 퀘스트를 그래프 노드로 구성하고, 모든 선행 노드가 완료 상태일 때만 다음 퀘스트가 해금되도록 통제합니다.
  • 상호 배타적 분기 노드: 진영 선택이나 도덕성 분기에서 한쪽을 선택하면 반대편 퀘스트 노드를 비활성화(Ineligible) 처리해 스토리 충돌을 차단합니다.
  • 위상 정렬(Topological Sort) 사전 검증: 퀘스트 데이터베이스 빌드 시 위상 정렬 알고리즘을 돌려 순환 참조(A를 깨려면 B가 필요하고, B를 깨려면 A가 필요한 버그)를 100% 검출합니다.

2. 퀘스트 수명 주기를 제어하는 유한 상태 머신(FSM)

치트 패킷을 원천 차단하는 엄격한 상태 전이 파이프라인:

  • 6대 표준 상태 정의: Locked(잠김) ➔ Available(수락가능) ➔ Active(진행중) ➔ Completed(완료) ➔ Claimed(보상수령) (실패 시 Failed 전이).
  • 서버 권한 상태 전이: 클라이언트는 완료 신호를 보낼 수 없습니다. 유저는 행동(사냥/채집)만 수행하고 서버가 목표 달성 여부를 검증한 후 상태를 바꿉니다.
  • 낙관적 UI 애니메이션: 서버 승인 패킷을 수신하는 즉시 클라이언트 HUD에서 목표 게이지가 차오르고 경쾌한 보상 사운드를 출력합니다.
ServerScriptService.QuestSystem.QuestManager
-- 유한 상태 머신 기반 퀘스트 관리자
local QuestManager = {}
QuestManager.__index = QuestManager

local QuestDatabase = require(game.ReplicatedStorage.QuestDatabase)

function QuestManager.new(player, profileData)
    local self = setmetatable({}, QuestManager)
    self.Player = player
    self.ActiveQuests = profileData.ActiveQuests or {} -- [questId] = {Step = 1, Progress = {}}
    self.CompletedQuests = profileData.CompletedQuests or {} -- 완료된 퀘스트 ID 셋
    return self
end

function QuestManager:CanStartQuest(questId)
    local data = QuestDatabase[questId]
    if not data then return false end
    if self.CompletedQuests[questId] or self.ActiveQuests[questId] then return false end
    
    -- DAG 선행 조건 검증
    for _, prereqId in ipairs(data.Prerequisites) do
        if not self.CompletedQuests[prereqId] then
            return false
        end
    end
    return true
end

function QuestManager:AcceptQuest(questId)
    if not self:CanStartQuest(questId) then return false end
    self.ActiveQuests[questId] = {
        Step = 1,
        Counters = table.create(#QuestDatabase[questId].Steps[1].Objectives, 0)
    }
    return true
end

return QuestManager

3. 이벤트 버스(Signal Bus) 기반의 목표 추적 시스템

게임플레이 루프와 퀘스트 검증 코드의 완전한 디커플링:

  • 중앙 집중형 게임 이벤트 버스: 몬스터 사망 스크립트에 퀘스트 코드를 직접 넣지 않고, 범용 EntityKilled(entityId, player) 신호를 발생시킵니다.
  • 동적 이벤트 필터링: QuestManager가 이벤트 버스를 구독하여 현재 진행 중인 퀘스트의 목표 조건과 일치할 때만 카운터를 증가시켜 CPU 부하를 없앱니다.
  • 복합 목표 처리: 약초 5개 수집 및 고블린 3마리 처치 같은 다중 목표를 정형화된 카운터 딕셔너리로 동시 추적합니다.

4. 분기형 대화 트리(Dialogue Tree) & 선택지 로직

선택에 따라 전개가 달라지는 상호작용형 NPC 대화 설계:

  • 노드 기반 대화 딕셔너리: NPC 대사를 카메라 앵글, 화자 텍스트, 그리고 플레이어 선택지 배열이 포함된 상호 연결 노드로 구조화합니다.
  • 조건부 선택지 필터링: 특정 퀘스트 진행 상태, 인벤토리 아이템 소지 여부, 평판 수치에 따라 숨겨진 대화 선택지를 동적으로 노출합니다.
  • 노드 진입 액션 페이로드: 대화 노드 선택 시 즉시 아이템 지급, 컷신 재생, 보스전 진입 등 게임 내 트리거를 실행합니다.

5. ProfileService 기반 비트필드 저장 압축 기법

수백 개의 퀘스트 완료 기록을 최소 바이트로 안전하게 영속화:

  • 비트필드(Bitfield) 패킹: 완료된 퀘스트 번호를 정수 1개의 32개 비트에 1:1 매핑하여 4바이트 정수 하나에 32개 퀘스트 완료 상태를 압축 저장합니다.
  • 진행 중인 상태 슬라이스: 현재 진행 중인 퀘스트의 ID와 세부 카운터만 저장하고 기본 메타데이터는 제외하여 용량을 95% 절감합니다.
  • 데이터 스키마 마이그레이션: 스토리 패치로 퀘스트가 수정될 때 ProfileService 버전 훅을 통해 기존 유저의 퀘스트 진행도를 오류 없이 보정합니다.

Frequently Asked Questions

왜 퀘스트 의존성을 DAG(방향성 비순환 그래프)로 모델링해야 하나요?

순환 참조(A를 깨려면 B가 필요하고, B를 깨려면 A가 필요한 교착 상태)를 수학적으로 100% 방지하고 선행 관계를 명확히 정의할 수 있기 때문입니다.

이벤트 버스(Signal Bus)는 퀘스트 성능을 어떻게 개선하나요?

모든 퀘스트가 매 프레임 아이템이나 몬스터 상태를 감시하는 대신, 사건이 발생했을 때만 신호를 받아 카운트를 올리므로 CPU 사용량이 거의 0에 수렴합니다.

갑작스러운 튕김 현상 시 퀘스트 데이터 손실을 어떻게 막나요?

ProfileService 세션 락을 사용해 카운터 변경 시 인메모리 캐시를 즉시 갱신하고 주기적 자동 저장과 종료 시 원자적 커밋으로 무결성을 보장합니다.

대화 트리에서 안전하게 퀘스트 보상을 지급하는 방법은?

대화 출력은 클라이언트에서 즉각 렌더링하되, 최종 보상 노드 선택 시 서버의 RemoteFunction을 호출하여 서버가 조건을 재검증한 후 보상을 지급해야 합니다.
