在 Roblox 中打造生动逼真的敌人——无论是生存恐慌中的追踪怪、RPG 副本机制 Boss，还是战术射击小队——最忌讳混乱的面条代码。将上百行 if-else 堆砌在单个脚本中，极易导致寻路死锁、逻辑冲突以及严重的服务器帧率雪崩。

工业级游戏开发通用方案为：宏观行为依赖有限状态机（FSM），微观战斗战术交由行为树（Behavior Trees）。本指南深入剖析黑板（Blackboard）数据总线、视锥（FOV）射线检测、仇恨机制，以及基于 AI LOD 的服务器 Tick 分帧调度方案。

1. 有限状态机（FSM）与行为树（Behavior Trees）架构选型

根据敌人复杂度与交互密度科学选型：

  • 有限状态机（FSM）： 适用于拥有明确生命周期的基础小怪：巡逻（Patrol）、警觉（Investigate）、追击（Chase）、攻击（Attack），具备独立的 Enter、Update 与 Exit 钩子。
  • 行为树（BT）： 专为应对复杂战术推演的高阶 Boss 设计（例如结合玩家血量自动选择拉开身位、释放霸体、寻找掩体或召唤随从）。
  • 混合架构推荐： 外层采用 FSM 划定宏观作战状态，在战斗状态内部挂接行为树解析瞬时微操。

2. 共享黑板（Blackboard）与视锥感知系统

在极低 CPU 负载下赋予 NPC 拟真的空间视觉感知：

  • 黑板模式： 集中式键值对数据表，用于在各节点与状态间共享 NPC 的战术记忆（当前目标、最后目击坐标、警觉警戒值）。
  • 视锥与视线检测： 结合向量点乘（Dot Product）验证玩家是否处于前方 110 度视场角内，并触发射线检测（Raycast）排查掩体阻隔。
  • 射线检测预算化： 切勿在 Heartbeat（60Hz）中为每个怪实时发线。将感知更新拉长为 0.2 至 0.4 秒一次，并在帧间错峰调度。

3. Production Implementation Architecture

ServerScriptService.NPCFramework.StateMachine
-- Modular Finite State Machine for Roblox NPC
local StateMachine = {}
StateMachine.__index = StateMachine

function StateMachine.new(npcInstance, states, initialState)
    local self = setmetatable({}, StateMachine)
    self.NPC = npcInstance
    self.States = states
    self.CurrentState = nil
    self.Blackboard = {
        Target = nil,
        LastSeenPos = nil,
        Health = 100,
        PatrolPoints = {}
    }

    self:ChangeState(initialState)
    return self
end

function StateMachine:ChangeState(newStateName)
    if self.CurrentState and self.States[self.CurrentState].Exit then
        self.States[self.CurrentState]:Exit(self.NPC, self.Blackboard)
    end

    self.CurrentState = newStateName
    if self.States[newStateName] and self.States[newStateName].Enter then
        self.States[newStateName]:Enter(self.NPC, self.Blackboard)
    end
end

function StateMachine:Update(dt)
    if self.CurrentState and self.States[self.CurrentState].Update then
        local nextState = self.States[self.CurrentState]:Update(self.NPC, self.Blackboard, dt)
        if nextState and nextState ~= self.CurrentState then
            self:ChangeState(nextState)
        end
    end
end

return StateMachine

4. 行为树核心节点机制：选择器、顺序器与装饰器

构建清晰的分层优先级决策链路：

  • 选择器节点（Selector, ?）： 从左至右依序执行子节点，任一子节点返回成功即刻中止并成功返回（尝试攻击 -> 距离过远则尝试追击 -> 丢仇恨则巡逻）。
  • 顺序器节点（Sequence, &）： 必须所有子节点按顺序依次成功才算成功（贴近目标 -> 播放前摇动画 -> 结算判定伤害）。
  • 装饰器节点（Decorator）： 控制子节点的返回值，用于添加技能 CD 冷却、反转真伪或执行循环。

5. 服务端大规模伸缩：AI LOD 与对象池化

保证 100+ 敌人同屏活动时服务器稳定维持 60 FPS：

  • AI 细节层级（LOD）： 玩家 100 Stud 内执行 10Hz 感知计算；250 Stud 外降频至 1Hz；500 Stud 以外完全冻结物理与射线运算。
  • 客户端移动平滑： 服务端仅同步粗粒度路径路标，客户端利用本地 Tween 或 CFrame 插值实现顺滑转身与步态动画。
  • 对象池（Object Pooling）： 严禁高频调用 Instance.new 与 Destroy。预热 NPC 对象池，通过切换透明度与 CFrame 实现怪物复用。

Frequently Asked Questions

为什么场景中超过 30 只怪物时服务器会明显卡顿？

因为所有怪物都在 60Hz 帧率下盲目执行射线检测与路径运算。必须引入 AI LOD，分帧摊薄感知频率。

行为树相比有限状态机的根本优势是什么？

行为树具备极强的模块插拔性，新增技能与行为逻辑无需修改错综复杂的状态连线，彻底规避状态爆炸。

如何彻底避免 NPC 隔墙透视发现玩家？

从 NPC 头部向玩家躯干投射射线，通过 RaycastResult 判定是否有墙壁掩体阻断视线通道。

能否将 NPC 的决策逻辑直接下放给客户端运算？

绝不能！所有寻路决策与伤害结算必须保留在服务端，防止外挂篡改数据。客户端仅负责动作与位移表现。
